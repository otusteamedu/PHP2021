## Разработка кейсов тестирования

Тестирование рассчитано на проверку валидатора данных на стороне бэкенда

### Модульные (Unit) тесты

Модульные тесты будут проверять валидатор данных. Предположим что это будет делать специальный метод, последовательно 
проверяющий валидность каждого поля пришедшего из формы. Тесты будут проверять работу метода с невалидными данными.

1. Проверка что JSON c данными сущетсвует. Если результат равен null, возвращаем код ответа 400;
2. Проверяем заполненность поля **card_number**. Если оно пустое, тестируемый метод должен вернуть код ответа 400 и 
текст ошибки;
3. Проверяем введенное значение в поле **card_number**, регулярным выражением `^\d{16}$`. Если проверка провалена, 
тестируемый метод должен вернуть код ответа 400 и текст ошибки;
4. Проверяем заполненность поля **card_holder**. Если оно пустое, тестируемый метод должен вернуть код ответа 400 и 
текст ошибки;
5. Проверяем введенное в поле **card_holder** значение. В случае наличия цифр или символов не относящихся к латинице 
(за исключением пробела и дефиса), тестируемый метод должен вернуть код ответа 400 и текст ошибки;
6. Проверяем введенное значение в поле **card_holder**. Поле должно содержать один пробел в середине строки, иначе 
тестируемый метод должен вернуть кот ответа 400 и текст ошибки;
7. Проверяем заполненность поля **card_expiration**. Если поле пустое, тестируемый метод должен вернуть код ответа 400 и 
текст ошибки;
8. Проверяем значения поля **card_expiration**, при помощи регулярного выражения `/^\d{2}\/\d{2}$/`. Если проверка 
провален, тестируемый метод должен вернуть код ответа 400 и текст ошибки;
9. Разбиваем значение поля **card_expiration** по разделителю **/** (слэш) и проверяем валидность месяца и года 
действительности карты. Для невалидных дат, тестируемый метод должен вернуть код ответа 400 и текст ошибки;
10. Проверяем заполненность поля **cvv**. Если оно пустое, тестируемый метод должен вернуть код ответа 400 и текст 
ошибки;
11. Проверяем значения поля **cvv**, при помощи регулярного выражения `^/\d{3}/$`. Если проверка провалена, тестируемый 
метод должен вернуть код ответа 400 и текст ошибки;
12. Проверяем заполненность поля **order_number**. Если оно пустое, тестируемый метод должен вернуть код ответа 400 и 
текст ошибки;
13. Проверяем количество символов в поле **order_number**. Если символов меньше 1 или более 16 тестируемый метод должен 
вернуть код ответа 400 и текст ошибки;
14. Проверяем заполненность поля **sum**. Если оно пустое, тестируемый метод должен вернуть код ответа 400 и текст 
ошибки;
15. Проверяем валидность данных в поле **sum**, при помощи регулярного выражения `^\d+,\d{2}$`. Если проверка провалена,
тестируемый метод должен вернуть код ответа 400 и текст ошибки.

### Интеграционные тесты

#### Проверка связки Фронтенд - Бэкенд

1. В случае незаполненности одного из полей бэкенд возвращает код ответа, 400 с текстом ошибки. На фронте, после 
получения ошибки, выделяется красной рамкой соответствующее поле и выводится текст ошибки: **Поле обязательно для 
заполнения**;
2. В случае ошибки валидации полей бэкенд возвращает код ответа 400 и текст ошибки. При получении ошибки, на фронтенде 
выделяется красной рамкой соответствующее поле и выводится текст ошибки **Неверный формат данных** и соответствующая 
подсказка (например, Номер карты должен состоять из 16 цифр);
3. В случае ошибки валидации JSON-объекта, бэкенд возвращает код ответа 400, а фронт при получении ошибки должен 
отобразить текст: **Ошибка отправки формы, перезагрузите страницу**;
4. Получив ответ 200 от бэкенда фронтенд, должен отобразить модальное окно с информацией об успешной оплате.

#### Проверка связки Бэкенд - Сервис А

1. Передаем заведомо неправильные данные в платежный сервис. Проверяем, что ответ сервиса содержит 403;
2. Передаем корректные данные в платежный сервис. Проверяем, что оплата прошла успешно и сервис ответил 200. Варианты 
снижения стоимости работы теста:
    * Поискать информацию на сайте Сервиса А, возможно у них есть функционал песочницы для тестирования оплат. Если 
   информацию найти не удастся, то стоит связаться с поддержкой. Если такого функционала нет, то стоит связаться с 
   специалистами из отдела интеграции Сервиса А и обсудить с ними возожность разработки подобного функционала;
    * Обартиться к коллегам хорошо знакомым с ассортиментом сайта и спросить у них какой из товаров на сайте обладает 
   наименьшей стоимостью и использовать для тестирования его. Если такой товар отсутсвует, то рассмотреть возможность 
   создания на сайте подобного тестового товара и варианты того каким образом скрыть его от обычных пользователей;
    * Написать скрипт, который будет вызываться после работы теста и отменять тестовый заказа возвращая деньги обратно 
   на счёт с которого они списывались.

#### Проверка связки Бэкенд - Репозиторий

1. Передаем в метод `setOrderIsPaid()`, несуществующий номер заказа. В ответ ловим исключение **Order with this ID 
not found**;
2. Передаем в метод `setOrderIsPaid()`, корректные номер заказа и сумму и проверяем, что вернулось `true`;
3. Передаем в метод `setOrderIsPaid()`, номер и сумму неоплаченного заказа. После завершения работы метода, делаем 
запрос к БД и проверяем что статус заказа изменился на оплаченный;
4. Передаем в метод `setOrderIsPaid()`, существующий номер заказа, но некорректную сумму. Получаем исключение 
**Неверная сумма для заказа $orderNumber**.

### Системные тесты

1. Вводим корректные данные несуществующей банковской карты, валидация при этом пройдёт успешно, но оплата не пройдёт. 
Сервис А вернёт на бэкенд код ответа 403. Бэкенд в свою очередь вернёт код ответа 403 в фронтенда, который должен 
отобразить сообщение: "Оплата не удалась, проверьте данные карты";
2. Вводим корректные данные существующей банковской карты, валидация на бэкенде пройдёт успешно и данные будут
переданные Сервису А, который после успелной оплаты вернёт код ответа 200. Затем бэкенд отправит данные о успешно
оплаченном заказе в репозиторий, методу `setOrderIsPaid()`, который обновит статус заказа в БД, на оплачен и верёнт 
бэкенду `true`, после чего тот отправит код ответа 200 на фронтенд. Проверяем что фронт выводит модальное окно с 
информацией об успешной оплате. Так-же делаем запрос в БД и проверяем статус и наличие указанного заказа, который должен
существовать и иметь оплаченный статус.
